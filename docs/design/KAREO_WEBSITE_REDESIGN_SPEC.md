# Kareo 網站改版實作規格（Website Redesign Specification）

> **文件版本**：v1.0｜2026-10-12  
> **資料來源**：《Kareo 網站改版建議》（檢視日期：2026-10-06，共 6 頁）  
> **適用對象**：Kareo 產品負責人、設計師、前端／後端工程師、QA、AI Coding Agent  
> **文件定位**：將改版建議轉換成可執行的需求、任務與驗收規範；**不是**網站現況的最新稽核報告。

## 0. AI Coding Agent／團隊執行指令

在動手修改程式前，請先閱讀此文件並遵守下列原則：

1. **先確認現況，再修改**：檢視目前分支、路由、畫面、API 和部署環境；PDF 記錄的是 **2026-10-06** 的觀察，不代表目前仍有相同問題。
2. **保留現有可用功能**：不得因視覺改版移除已正常運作的功能、權限驗證或必要的資料保護措施。
3. **優先處理 P0**：資訊入口與真實開放狀態一致、同意／個資處理可用性與正式上線門檻，高於 Logo 或裝飾性設計。
4. **以實際功能為準**：不得使用尚未實現的服務承諾；例如「已審核發布」「可刪除資料」「補助資格已核定」等文字，需有真實功能或證據支持。
5. **不得以測試代替法務與資安確認**：涉及真實敏感資料、正式告知、保存、刪除及撤回的內容，須經專責人員核對後才能宣稱正式開放。
6. **保留設計的一致性**：原站的深綠、淡灰綠、白色卡片是已觀察到的方向；以漸進式改善為主，不需先全面重畫品牌。
7. **每項任務需回報**：修改檔案、影響頁面、測試方式、已知限制、尚待驗證項目；無法確認者標記 `待驗證`，不得標示 `已完成`。

**標記規則**：
- **[PDF 觀察]**：報告檢視時所見的內容或狀態。
- **[PDF 建議]**：報告提出的改善方向，尚非驗證後的效果。
- **[延伸規格]**：為方便開發與驗收，依報告原則整理的實施細節；不是報告對目前程式架構的事實敘述。
- **[待驗證]**：現有證據不足，須實測、查程式或由產品／法務確認。

## 1. 改版目標與範圍

### 1.1 核心目標

讓首次使用 Kareo 的人能夠：

1. 在首頁迅速理解：**Kareo 可以協助整理長照需求、提供初步資訊與下一步方向**，而非正式資格核定機關。
2. 清楚找到 **「開始免費長照評估」**，知道大約所需時間與是否需要登入。
3. 分辨 **資訊已開放、尚未開放或暫時故障**，不被相互矛盾的狀態文案誤導。
4. 在評估前理解資料用途與限制，並能找到資料相關說明。
5. 在服務無法使用時，仍可找到替代的下一步，例如 **長照專線 1966**。
6. 使用手機、鍵盤、文字放大功能時，仍能辨識重要資訊、操作與錯誤恢復方式。

### 1.2 受眾（測試假設，非已證實輪廓）

- **家庭照顧者**：可能替家人蒐集與整理長照資訊。
- **可自行操作的長者**：可能直接查看制度資訊或開始評估。

**[待驗證]** 誰是第一優先受眾、是否真正支援家屬代填、流程如何呈現代填角色，需先確認實際產品設計。

### 1.3 本次範圍

| 頁面／流程 | 本次需求 | 狀態界定 |
| --- | --- | --- |
| 桌面首頁 | 內容層次、CTA、服務邊界、視覺一致性 | PDF 已檢視 |
| 長照資訊頁 | 開放狀態、錯誤處理、替代行動、來源資訊 | PDF 已檢視 |
| 服務說明／同意頁 | 正式／測試環境區分、資料告知與相關流程 | PDF 已檢視 |
| 初步評估流程 | 步驟、返回、錯誤、進度與結果說明 | **PDF 未走完整流程，須盤點後實作** |
| 結果頁 | 結果範例、資料刪除／撤回入口、下一步 | **PDF 未檢視，全部待驗證** |
| 手機版、鍵盤、縮放、對比 | 需要補做測試 | **PDF 尚未檢測** |

### 1.4 非目標

- 不重新設計整套企業識別系統（CIS）或立即更換 Logo。
- 不假定現有 API、資料保存／刪除、結果頁等功能已完成。
- 不把初步評估說成政府正式核定、專業醫療診斷或保證取得補助。
- 不因為符合本文件的部分項目，就宣稱「全站符合 WCAG 2.2 AA」或已取得無障礙標章。

### 2.1 P0 — KUI-001：修正長照資訊頁

**[PDF 觀察]** 首頁承諾可瀏覽「已審核發布」資訊，但資訊頁顯示「暫時無法取得資訊」與「此功能尚未開放」；報告當時重試一次仍相同。**沒有診斷出後端原因。**

**實作步驟**

- [ ] 查明該功能在目前環境屬於：`AVAILABLE`（已開放）／`COMING_SOON`（尚未開放）／`TEMP_ERROR`（暫時故障）。
- [ ] 若 `AVAILABLE`：顯示真實可取用內容，確保首頁入口能連到可用功能。
- [ ] 若 `COMING_SOON`：明確寫「功能籌備中」，移除無效篩選、無效重試按鈕及「已審核發布」等不符現況的承諾。
- [ ] 若 `TEMP_ERROR`：顯示可理解的故障說明，提供有效重試與替代行動。
- [ ] 區分 `LOADING`／`EMPTY`／`ERROR`，不得把「無資料」等同「功能未開放」。**[延伸規格]**
- [ ] 可用內容顯示來源、更新日期、維護者；若資料欠缺，標記待補，不得捏造。
- [ ] 確認服務頁面的按鈕和導覽在桌面與手機皆可操作。

**驗收條件**

- [ ] 使用者從首頁進入資訊頁後，不會看到彼此衝突的功能狀態。
- [ ] 對於未開放功能，不存在會造成誤解的篩選器／重試操作。
- [ ] 對於暫時故障，至少有一個有效的恢復或替代下一步。
- [ ] 開放中的資訊有可查核的來源與更新紀錄，或清楚標明尚待補足。

### 2.2 P0 — KUI-002：確認同意流程與正式上線門檻

**[PDF 觀察]** 同意頁標示文案「尚未經法務確認，非正式核准版本」，且保存清理、結果頁刪除與撤回等項目需完成驗證後才正式開放。**此為就緒度與信任風險，不能直接據此作違法判定。**

**產品須先決定**：目前是 `TEST`（測試版）或 `PRODUCTION`（正式版）？此欄位不可只依 UI 文字猜測。

**測試版（TEST）**

- [ ] 清楚標示「測試環境／測試用途」及適用範圍。
- [ ] 以事先建立的**虛構案例**進行測試；避免蒐集測試者與家人的真實健康等敏感資料。
- [ ] 無法保證的儲存、刪除或撤回功能不得寫成已開放。
- [ ] 若目前可以實際送出個資，須先由產品／工程審核處理方式與風險。

**正式版（PRODUCTION）上線前**

- [ ] 確認告知資訊內容與實際使用／蒐集情境相符。
- [ ] 工程師逐項驗證資料保存、清理、刪除與撤回的實際操作行為及限制。
- [ ] 由適當負責人確認正式服務說明、同意與隱私文案。
- [ ] 評估頁、結果頁及相關入口的敘述一致，且不存在未實現的承諾。
- [ ] 在上述驗證完成前，不將網站描述成已具備完整正式資料處理機制。

**驗收條件**：能用測試紀錄證明文案與實際行為對應；風險項目有負責人、處理狀態及上線阻擋決策。

### 2.3 P1 — KUI-003：清楚說明服務對象與評估完成後的內容

**[PDF 觀察]** 首頁有用途與時間提示，但沒有清楚區分本人自填或家屬代填，也沒有展示結果範例；完整評估和結果頁未被檢視。

**建議內容順序**

1. 我能用 Kareo 做什麼？
2. 如何開始免費初步評估？
3. 完成後可能看到什麼？
4. 這些資訊**不能代替**什麼？

**示意步驟文案 [PDF 建議；功能須確認]**：

`回答生活狀況 → 看初步建議 → 了解正式申請方式`

**實作步驟**

- [ ] 查核是否支援本人與家屬代填；未支援者不出現虛假的模式選擇。
- [ ] 查核評估完成的真實內容，再設計範例畫面；範例須標示「示意」。
- [ ] 每個步驟顯示下一步及返回方式；返回後資料是否保留，依真實行為撰寫文案。**[延伸規格]**
- [ ] 評估尚未核定或完成前，不使用「確定符合補助資格」等暗示正式核定的語句。
- [ ] `3–5 分鐘`、`免費`、`不需登入` 是 PDF 當時首頁所示的承諾，正式發布前應再實測確認。

**驗收條件**：不熟悉 Kareo 的受測者可以用自己的話解釋平台用途、評估限制及下一步。

## 3. 頁面資訊架構與文案

> 以下是**建議內容與結構**，而非對現有路由或實際 API 的斷言。實際 URL 與導覽需依程式確認。

### 3.1 首頁：四區塊內容順序

| 區塊 | 建議內容 | 設計注意 |
| --- | --- | --- |
| **01 說明用途** | H1：「先整理長照需求，了解下一步」 | 這是待測試主標，不暗示核定資格或補助 |
| **02 開始評估** | 主要 CTA：「開始免費長照評估」 | 全頁只有一個最高強度主按鈕；旁列免費、不需登入、約 3–5 分鐘（需驗證） |
| **03 先查資訊** | 次要 CTA：「查看長照制度與補助」 | 內容可用才作正式入口，未開放時明確標示並提供替代行動 |

**首頁 Hero 參考文案 [PDF 建議＋延伸排版]**

> **[開始免費長照評估]**  
> 約 3–5 分鐘｜免費｜不需登入（**正式上線前請驗證**）  
> 查看長照制度與補助（**依功能開放狀態顯示**）

### 3.2 資訊頁：依真實狀態呈現

| 狀態 | 標題／訊息示例 [延伸規格] | 主要可執行操作 |
| --- | --- | --- |
| `LOADING` | 「正在載入長照資訊…」 | 保持頁面及焦點可理解 |
| `AVAILABLE` | 「長照制度與補助資訊」 | 瀏覽實際內容；顯示來源／更新日期／維護者 |
| `EMPTY` | 「目前沒有符合條件的資訊」 | 清除篩選／返回資訊列表（如實際支援） |
| `COMING_SOON` | 「長照資訊功能籌備中」 | 查看其他已開放服務／撥打 1966 |
| `TEMP_ERROR` | 「目前無法載入資訊，請稍後再試」 | 重試／返回首頁／撥打 1966 |

**狀態設計規則**

- 不同狀態不得共用會造成矛盾的文字（例如同時表示「尚未開放」和「暫時故障」）。
- `COMING_SOON` 不顯示無效篩選器；`TEMP_ERROR` 才提供真正可重新觸發的重試。
- 錯誤文案不用只靠紅色區分，需有文字說明與可行行動。
- 有資料時保留資訊來源、最後更新日期與維護者；未有真實資料時不虛構欄位內容。

### 3.3 同意頁：把限制與資料流程說清楚

頁面應能讓使用者找到（正式版本須由專責人員審核）：

- 服務與評估性質及用途。
- 實際蒐集何種資料、作何用途。
- 資料保存、清理、刪除與撤回方式及已知限制。
- 正式評估與補助核定需由適當的政府／專業服務流程辦理。
- 可查找說明的入口及替代聯繫方式（例如 1966）。

**禁止情況**：若尚未完成驗證，卻在頁面聲稱使用者一定能刪除、撤回或已取得法律正式核准。

### 3.4 初步評估／結果頁：僅在盤點後延伸

**[待驗證]** 報告未測試完整流程，因此下列是待確認的 UX 檢查，不是已發現的缺陷：

- [ ] 評估每步是否可辨識正在做什麼、還剩什麼。
- [ ] 返回上一步是否能修改答案，是否會意外遺失資料。
- [ ] 表單欄位是否有標籤、提示與清楚的驗證錯誤。
- [ ] 若中斷或失敗，是否有合理恢復方法。
- [ ] 結果是否清楚區分「初步整理／預估」與「正式核定」。
- [ ] 結果頁若聲稱可刪除、撤回資料，相關功能是否確實運作。

## 7. 五人任務測試（探索性研究）

### 7.1 招募與方式

- **建議先招募**：3 位有照護資訊查找經驗的家庭照顧者、2 位可自行操作的長者。
- 涵蓋不同數位熟悉度；使用受測者熟悉的裝置或輔具，保留休息時間。
- **每人約 25–35 分鐘**。
- 全程使用預先準備的**虛構照護情境**，不要求輸入本人或家屬真實健康資料。
- 主持人先觀察，必要時再協助；記錄協助發生的位置及受測者原話。

### 7.2 共同任務腳本

1. **理解用途**：看首頁後，用自己的話說明 Kareo 能幫什麼、初步結果是否等於正式核定，並找到「開始免費長照評估」。
2. **操作評估**：使用虛構案例操作兩個評估步驟，返回修改答案，再指出進度與下一步。
3. **查找資訊**：找到一項長照制度或補助資訊；若目前不可用，找出替代下一步。
4. **理解資料使用**：找到資料用途、保存、刪除／撤回相關說明；若功能尚未上線，能清楚辨識。

### 7.3 每位受測者的紀錄欄位

| 受測者 | 任務 | 無協助完成？ | 卡點／錯誤 | 能否恢復？ | 重要原話 | 理解是否正確？ | 後續處理 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| P01–P05 | T1–T4 | 是／否 |  |  |  | 是／否 |  |

### 7.4 下一輪內部門檻

報告提供的**內部建議**為：

- **沒有未解決的重大誤解**；且
- **核心任務至少 4／5 位受測者能無協助完成**。

這是**探索性測試與內部修正門檻**，**不是統計代表性結果或正式無障礙認證**；有重大錯誤時仍須先修正並複測。
